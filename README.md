# Harbor

An open-source prototype of a contingent-work system of record for small and mid-market companies. Harbor models the people who work for a business but are not on its employee payroll: agency temps, independent contractors, and simple project talent.

**This is a synthetic-data customer demo, not a production VMS.** Brightline, its people, suppliers, rates, hours, invoices, and payments are fictional. Payment buttons only update local demo state; they do not move money.

## Run locally — no secrets required

Requirements: **Node.js 22** and **pnpm 10.18.0**. No database, account, API key, or `.env` file is required for the static demo.

```sh
# Clone this repository, then enter its directory.
npm install --global pnpm@10.18.0
pnpm install --frozen-lockfile
pnpm dev:static
```

Open **http://localhost:3000**. On macOS/Linux, choose another port with `PORT=3001 pnpm dev:static`. The development command uses POSIX shell variable syntax; on Windows use WSL or run `pnpm exec vite --host 0.0.0.0 --port 3000 --strictPort` directly.

```sh
pnpm check          # TypeScript checks
pnpm test           # Existing server/platform unit tests
pnpm build:static   # Static output in dist/public
pnpm exec vite preview --host 127.0.0.1 --port 4173
```

Static hosting should serve `dist/public` and rewrite application page routes to `index.html`. Do not rewrite asset requests indiscriminately. `dist/public/api/platform/config.js` is generated by the build; the demo works with empty platform configuration. Logo assets are included locally. Google Fonts is optional; system font fallbacks are provided.

## Demo: switch seats, keep the same ledger

The persistent top bar changes the persona and returns to that persona's home. All five seats read the same browser-local ledger. **Reset** restores the seed. Changes survive refresh in the same browser through `localStorage`; they are not shared across browsers, machines, or visitors.

Each home includes a **Do this next** cue. Suggested walkthroughs:

| Persona | Major jobs to demonstrate |
| --- | --- |
| **Maya Chen — People Ops** | Inspect live engagements and spend; review classification, document, tenure, and rate flags; record a human attestation; clear exceptions; activate a ready engagement. |
| **Priya Shah — hiring manager** | Describe a staffing need; review a rule-based draft with type and rate band; rehire an alumni or open the request to Northwind; shortlist/offer candidates; approve submitted time. |
| **Jordan Hale — staffing supplier** | Review Brightline requests; submit a candidate with rate and availability; watch submission status change after the manager shortlists/offers; track supplier invoices. |
| **Elena Ruiz — finance** | Inspect department payables and invoice coding; accept a submitted project deliverable in the demo; release an individual payable or the demo ACH batch; see statuses update across seats. |
| **Sam Okonkwo — worker** | Accept an offered assignment if present; complete checklist items; submit hours; see approval, scheduled payment, and paid status. |

### Cross-persona time-to-pay story

1. **Reset** and switch to **Sam**. Submit the seeded assignment's hours.
2. Switch to **Priya** and approve Sam's submitted time. Harbor creates a payable and scheduled demo payment.
3. Switch to **Elena** and release Sam's invoice or the demo batch.
4. Return to **Sam** to see the payment marked paid. The same records drive each seat.

### Sourcing story

1. As **Priya**, draft a request and open it to Northwind.
2. As **Jordan**, submit a candidate against a sourcing request.
3. As **Priya**, shortlist/offer the candidate. The person and engagement appear on the ledger.
4. As **Jordan**, show the updated submission status. As **Maya**, inspect the resulting engagement.

The worker persona is fixed to Sam; it is not an impersonation interface for newly submitted candidates.

## Architecture

| Path | Responsibility |
| --- | --- |
| `client/src/App.tsx` | React application routes and provider composition. |
| `client/src/components/AppShell.tsx` | Persona switcher, navigation, demo reset. |
| `client/src/context/PersonaContext.tsx` | Active demo persona and subscriptions to ledger state. |
| `client/src/types.ts` | Typed people, requests, engagements, time, milestones, invoices, and payments. |
| `client/src/data/seed.ts` | Fictional Brightline seed and persona definitions. |
| `client/src/data/store.ts` | In-memory ledger, localStorage persistence, and demo mutations. |
| `client/src/lib/demoNext.ts` | Persona-specific next-step cues. |
| `client/src/pages/` | Role-specific workspaces and shared detail pages. |
| `client/src/components/ui/` | Reusable Radix/shadcn-style UI components. |
| `client/src/index.css` | Harbor's warm neutral/teal visual theme. |
| `server/`, `drizzle/`, `shared/` | Retained Express/tRPC/Drizzle starter and optional integration helpers; not a persisted contingent-work backend. |
| `vite.config.ts` | Static development/build, aliases, public configuration, and development debug instrumentation. |

The current demo uses **React 19, TypeScript, Vite 7, Tailwind CSS 4, and Wouter**. The optional server starter includes Express, tRPC, Drizzle, and MySQL helpers. `pnpm dev` runs that starter server; it is not needed for the static demo and does not persist the contingent-work ledger. Optional managed-service helpers need separately configured credentials if adopted. Public configuration is explicitly whitelisted in `server/_core/publicConfig.ts`.

## What is implemented vs. simulated

- **Implemented:** persona-specific views, shared typed demo records, local persistence, request and candidate actions, checklist actions, flag resolution, time approval, invoice/payment status transitions, and demo reset.
- **Simulated:** AI drafting/classification/rate suggestions (deterministic rules, not live model calls); Slack-style UI (no Slack connection); document collection/e-signature (checklist state, no actual upload/signature verification); ACH/payment settlement (local state only).
- **Not implemented:** real authentication/authorization, tenant isolation, server-side contingent-work storage, production accounting/payroll/payment integrations, reliable idempotent financial processing, or a compliance decision engine.

Known prototype shortcuts include fixed demo dates, Sam-specific worker context, simplified state transitions, and limited checks for repeated approvals, offer issuance, and time edits after payment. Existing tests cover starter/platform behavior, **not** the full contingent-work workflow. Do not use real worker data, credentials, banking information, or legal records in the demo.

## Good next contributions

1. Add domain workflow tests and harden transitions/idempotency before extending simulated payments.
2. Replace localStorage with a tenant-aware API and durable database while preserving the domain model.
3. Add real authentication and enforce role-scoped access server-side; persona switching is only a presentation feature.
4. Make offer/onboarding flows reusable for any worker and preserve prior engagement history.
5. Move milestone acceptance to the accountable hiring manager with an audit trail.
6. Add optional AI drafting with human review, evidence, and secret-free client bundles.
7. Add production integrations only after accounting, privacy, compliance, and payment requirements are defined.
